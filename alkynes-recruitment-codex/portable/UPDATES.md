# 앱 업데이트 배포

이 기능을 처음 설치할 때는 Windows ZIP을 한 번 설치해야 합니다. 이후에는 설정 → 앱 업데이트에서 공개 GitHub 저장소를 지정하고 업데이트 확인 → 새 버전 업데이트를 누릅니다. 저장소 변경 시 설정에서 수정할 수 있습니다. GitHub 토큰을 앱에 넣지 않습니다. 비공개 저장소는 현재 지원하지 않습니다.

현재 패키지는 배포 주소가 연결되지 않은 상태입니다. GitHub 정식 릴리스와 아래 두 asset을 공개한 뒤 앱에 `소유자/저장소`를 입력해야 합니다. 빈 저장소·릴리스 누락·네트워크 실패는 오류로 표시하며 최신 버전이라고 잘못 표시하지 않습니다.

## 릴리스 만들기

루트 `.github/workflows/recruitment-release.yml`은 `recruitment-v2026.10.14.5` 같은 태그를 푸시할 때 테스트·정적 빌드·업데이트 파일 생성 후 GitHub 릴리스를 만듭니다. 먼저 이 소스와 워크플로를 저장소에 반영해야 합니다. 다음 배포에는 설치된 버전보다 큰 숫자 버전을 사용합니다. 현재 버전은 `portable/version.json`에 있습니다.

수동 배포 시 다음 명령으로 Windows 패키지 폴더에서 업데이트 파일만 생성합니다:

```
node scripts/package-update.cjs /path/to/windows-package /path/to/release
```

생성한 `alkynes-update.json`, `alkynes-update.json.gz`를 같은 최신 정식 릴리스의 assets로 업로드합니다. gzip 파일은 앱 화면·서버 코드·버전만 포함합니다. PC별 연결 경로, config, 브라우저 데이터, Node 런타임, 이력서·Excel 원본은 포함하지 않습니다.

## 적용 방식

설정에 지정한 공개 GitHub 저장소의 최신 릴리스만 읽습니다. HTTPS 주소와 파일 크기를 제한하고 SHA-256을 검증합니다. 파일 경로를 검증하여 허용된 앱 파일만 staging에 기록합니다. 현재 실행 중인 worker가 서버 종료 후 앱을 교체하며 config·Node 런타임은 교체하지 않습니다. 새 버전 health 응답을 확인한 뒤 완료 처리하며, 실패하면 이전 앱을 복원합니다. 최근 이전 버전은 `.updates/previous`에 남습니다. 프로세스 강제 종료나 전원 차단 중 파일 교체까지 보장하는 방식은 아닙니다.

브라우저 데이터와 연결 설정은 같은 주소에서 유지됩니다. 업데이트 전에 설정 → 데이터 백업을 사용할 수 있습니다. 실제 Windows 설치·보안 정책·재부팅은 회사 PC에서 확인해야 합니다.


## SQLite 저장 버전 (2026.10.16.5)

첫 적용은 기존 앱 업데이트 버튼으로 진행합니다. 새 서버와 site 폴더의 공통 검증기가 함께 교체되며 별도 SQLite 설치는 필요하지 않습니다. 원본 DB는 config/recruitment.sqlite에 생성하므로 기존 worker도 DB를 이동·덮어쓰지 않습니다. 처음 열린 기존 브라우저 자료를 DB로 이전하고 원본을 DB 내 별도 보관합니다. 설정에서 「노트북 SQLite 저장」과 DB 경로를 확인할 수 있습니다. 업데이트 실패 복원 시에도 config/DB 파일은 유지됩니다.

## 업무 편의 기능 (2026.10.19.4)

- 대시보드 「오늘 챙길 일」에서 오늘 면접, 미안내 일정, 인적성 응시기한, 기한 초과 요청을 확인합니다. 종료된 지원자·채용은 제외합니다.
- 카톡 안내문에서 지원자 안내/사내 공유를 각각 완료로 표시합니다. 복사만으로는 완료 처리하지 않으며, 원본 정보가 변경되면 재안내 대상으로 표시합니다. 실제 카카오톡 발송을 감지하거나 자동 발송하지 않습니다.
- 엑셀 변경 내역은 수정일별로 누적 기록하며, 같은 내용 재연동 시 중복 변경을 남기지 않습니다. 과거 실제 전형 변경일을 추정하지 않고 앱 반영 시각으로 기록합니다.
- 엑셀 원본 일시·장소·진행상태는 원본에서 수정합니다. 연락처·이력서·개인 메모·인적성 응시기한/실시 상태·면접 소요시간은 앱에 보관합니다. 면접 소요시간 미입력 시 일정 겹침 확인과 ICS 파일은 기본 60분을 사용합니다.
- 면접 카톡 기본 장소는 기존 고정 문구를 유지합니다. 엑셀 장소와 다른 경우 공유창에서 차이를 알려주므로 실제 장소에 맞게 안내문을 확인합니다.
- Windows 기본 자동 백업 폴더는 사용자 문서의 `AlkynesRecruitmentBackups`입니다. 설정에서 경로를 변경하고 별도 위치에 보관할 수 있습니다. 다른 운영체제/테스트에서는 데이터 폴더의 `backups`를 사용합니다.
- 앱 사용·저장 시 당일 백업을 갱신하며, 날짜별 30개·수동 20개·복원 직전 10개를 각각 유지합니다. 백업 폴더 접근 실패는 DB 저장 성공과 구분해 경고합니다. 복원 전 백업이 실패하면 기존 DB를 덮어쓰지 않습니다.
- 백업 파일에는 개인정보가 포함됩니다. 동일 노트북의 파일만으로는 기기 고장까지 대비할 수 없으므로 필요에 맞게 별도 저장 장치를 지정합니다. 백업 복원 후 엑셀 자동 연결이 켜져 있으면 원본 항목은 다음 연동 시 다시 갱신됩니다.


## 대시보드와 수정 이력 개선 (2026.10.19.5)

- 캘린더는 요약 카드 바로 아래에 배치합니다. 오늘 챙길 일은 우측 이번주 면접 위의 포스트잇으로 이동하고, 미완료 항목이 있을 때만 배경과 표시등을 반복 강조합니다. 모션 감소 설정에서는 정적인 테두리로 강조합니다.
- 대시보드의 엑셀 변경 내역은 제거합니다. 엑셀 연동 화면에서 날짜를 선택해 그날 여러 번 수정한 내역을 함께 확인하고, 지원자·공고·비고 등으로 검색할 수 있습니다.
- 최근 30회 제한을 제거합니다. 변경 없는 재확인은 이전 수정 이력을 덮어쓰지 않으며, 비고를 포함한 원본 A~P열·면접장소·면접관의 이전/변경 값을 기록합니다. 숨김 집계 열은 변경 기록 대상이 아닙니다.
- 수정일은 연결 파일의 저장 시각을 기준으로 묶으며 앱 반영 시각도 별도로 표시합니다. 예전 기록에 파일 저장 시각이 없으면 앱 반영일을 사용합니다. 네이버웍스 동기화 시 파일 타임스탬프가 바뀔 수 있으며 실제 편집자나 모든 중간 저장본을 추적하는 방식은 아닙니다.
- 새 필드 비교는 업데이트 후 첫 재연동부터 원본 값을 보관합니다. 이전에 저장하지 않았던 과거 변경이나 앱이 확인하기 전에 덮어쓴 중간 저장본은 소급 복원하지 않습니다.

## 레코드 저장·서버 자동 연동 (2026.10.27.1)

앱 업데이트 후 노트북 서버가 엑셀을 약 5초마다 확인합니다. 브라우저는 닫아도 됩니다. 노트북 전원·서버·네이버웍스 동기화는 실행 중이어야 하며, 자동 연결 중지 설정은 유지됩니다. 처음 SQLite를 사용하는 기존 브라우저 자료는 앱을 한 번 열어 이전해야 합니다.

기존 단일 JSON DB는 검증 후 records 테이블과 attachments 테이블로 이전됩니다. 이전 직전 전체 자료는 config/before-entity-migration-*.json과 일관된 SQLite 사본 config/before-entity-migration-*.sqlite에 보관합니다. SQLite 사본은 WAL까지 반영한 완전한 DB입니다. 평상시 화면 조회에는 이력서 본문을 보내지 않고, 이력서 열기와 전체 백업에서만 읽습니다. 업데이트 실패 복구와 별도로, 저장 구조가 바뀐 DB를 구버전 서버에서 직접 열어 사용하는 것은 지원하지 않습니다. 구버전으로 수동 복귀해야 한다면 서버를 정지한 상태에서 이전 직전 SQLite 사본으로 복구하거나, 정상 실행되는 앱에서 전체 JSON 백업을 복원하세요. 현재 DB 파일은 별도로 보존한 뒤 복구합니다. 기존 DB의 데이터를 비우거나 초기화하는 우회 방법은 사용하지 마세요.

이름이나 채용건명을 변경하려면 엑셀 연동의 ‘고유번호 포함 사본 다운로드’를 이용해 고유번호 4열을 유지하세요. 원본은 자동 수정하지 않습니다. 사본은 별도 파일이며, 기존 수식을 보존하려면 사본의 숨김 고유번호 열만 기존 파일의 빈 열에 복사할 수 있습니다. 고유번호를 삭제하거나 다른 사람의 번호를 복제하지 마세요. 새 요청·새 면접을 위해 행을 복사할 때는 새 행의 요청·면접 고유번호를 비우고, 같은 지원자라면 지원자 고유번호는 유지합니다. 번호가 없고 연결이 모호한 이름 변경은 자동으로 합치지 않고 반영을 중단합니다. 입력 형식 오류·연결 오류 시 마지막 정상 자료를 보존하며, 경고는 엑셀 연동의 입력 점검에서 확인합니다.

엑셀 동기화와 수동 입력은 동일한 DB 저장 버전으로 충돌을 검사합니다. PC·모바일 하단 진단에서 원본 저장시간, 앱 반영시간과 현재 데이터 버전을 확인할 수 있습니다. 파일 크기·첨부 제한이 모두 없어지는 것은 아니며, 서버와 디스크 여유 공간이 필요합니다.

## 백업·삭제·업무 보완 (2026.10.27.3)

- 자동 백업은 하루 첫 백업 30개, 변경이 발생한 시간의 첫 백업 168개, 변경 시점 백업 200개를 보관합니다. 저장을 1초 간격으로 묶으므로 매 타이핑·매 중간 상태를 복구하는 방식은 아닙니다. 수동 20개, 대량 변경 전 30개, 복원 전 10개를 별도로 보관합니다. 같은 날의 최초 정상 사본을 덮어쓰지 않습니다. 설정에서 복원 전 건수와 지원자 상태 차이를 확인할 수 있습니다.
- 기존 지원자가 3명 이상이면서 25% 이상 원본에서 제외되거나, 주요 정보가 5명 이상이면서 50% 이상 변경되면 보류합니다. 기존 Excel 면접의 3건 이상·25% 이상 제외 또는 3건 이상·50% 이상 일정/상태/장소/면접관 변경도 보류합니다. 엑셀 연동에서 원본을 확인한 후 승인하면 직전 백업을 남깁니다. 승인 후 파일이 바뀌면 다시 확인해야 합니다.
- 설정의 개인정보 관리에서 전형 종료/원본 제외 지원자의 보관 점검 기준을 지정하고 직접 삭제할 수 있습니다. 보관 점검일은 기록의 최근 변경일 기준입니다. 자동 개인정보 삭제는 하지 않습니다. 현재 기록, 내부 이력, 현재 관리하는 백업 폴더와 DB 이전용 JSON 사본을 정리하며, 이전용 SQLite 사본은 삭제합니다. 개인정보 삭제 확인 문구를 입력해야 실행됩니다. 익명 채용 기록과 삭제 고유번호를 유지해 같은 번호의 원본·과거 백업에서 개인정보가 다시 들어오지 않도록 합니다.
- 이미 내려받은 백업, 예전에 지정한 다른 백업 폴더, Excel/네이버웍스 원본, OS·클라우드의 버전 기록은 이 기능으로 삭제하지 않습니다. 별도로 관리해야 합니다. 논리적 삭제·DB 정리이며 디스크 포렌식 수준의 영구 소거 보장은 아닙니다.
- 이력서 연결을 제거하면 해당 PDF의 직접 조회도 차단합니다. 내부 최근 저장 이력에서 더 이상 참조하지 않는 PDF는 정리합니다. 전체 개인정보 삭제 기능은 해당 기록의 이력과 관리 중인 사본도 함께 처리합니다.
- 이름·공고 연결·연락처·메모·안내문 등 항목별 변경 전후를 새 저장부터 기록합니다. 과거 누락된 변경은 소급 복구하지 않습니다. 지원자 진행 이력과 설정의 상세 변경 이력에서 확인합니다.
- 일반 앱 저장은 변경 항목만 전송하고, 기존 자료 확인 시 버전이 같으면 본문을 생략하며 최근 5회 이내 버전에서는 바뀐 레코드만 받아 PC·모바일 화면에 적용합니다. 이력서는 기존처럼 별도 조회합니다. 최초 열기·새 버전 자료 갱신·전체 백업/복원은 전체 업무 자료를 사용할 수 있습니다. 지원자 목록은 30명씩 표시합니다.
